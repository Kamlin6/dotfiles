## 1. 审查摘要

DESIGN-001 整体结构清晰、ADR 记录完整、扩展性考虑周到，是**份量扎实的设计文档**。但 Zero-Trust 审查发现了若干**严重问题**：

- **1 个 P0 矛盾**：设计声称"向后兼容"，但 `default` profile 开启 VAD 的行为与 Sprint 0 代码**直接冲突**
- **1 个 P0 遗漏**：基准测试缺少任何**转录质量指标（WER）**，使得整个性能评估无法回答"变好还是变差"的根本问题
- **4 个 P1 问题**：M1 热降频未考虑、`threshold=0.3` 选择理由不足、边界条件未处理、Sprint 2 chunk 嵌套风险
- **多个 P2/P3 细节问题**：profile 语言字段声明与实际不符、合成音频方案过于单一、缺少 `--profile help` 便利功能等

**审查结论：需回流。** 建议在进入 CODE 阶段前修复 P0 问题，至少书面回复 P1 问题的处理方案。

### F-01 [P0] 「向后兼容」原则与 `default` profile 启用 VAD 冲突

**发现位置**: DESIGN 第 1 章"设计原则" vs 附录 A 参数映射

**描述**:
设计文档第 1 章声明：

> **向后兼容** — 不传 `--profile` 时行为与 Sprint 0 完全一致

但当前 Sprint 0 代码（`transcribe` 脚本第 56 行）调用的是：
```python
segments, info = model.transcribe(args.audio_path, language=args.language)
```
**没有传入任何 VAD 参数**。而 `default` profile（附录 A）设置了：
```python
"vad_filter": True,
"vad_parameters": { ... }
```
这意味着 Sprint 1 的代码在无 `--profile` 情况下会**启用 VAD 过滤**，与 Sprint 0 的**无 VAD 行为**完全不同。这不是"向后兼容"，而是静默的行为变更。

**影响**:
- 用户在升级后直接运行 `transcribe meeting.mp3`（无 profile 参数）会得到不同的转录结果
- VAD 过滤会移除被判定为非语音的片段，可能导致结果**丢失**部分原本 Sprint 0 能输出的内容
- 如果用户没有追踪工具版本，可能认为转录质量下降
- 违反了自己声明的设计原则

**建议修复方案**:
方案 A（推荐）：`default` profile 的 VAD 默认应与 Sprint 0 一致（即 `vad_filter=False`），VAD 仅由 `--profile monologue/voicelines` 显式启用。这样裸调用行为不变。

方案 B：若 design 团队认为默认启用 VAD 是正确方向，则必须：
1. 删除"向后兼容"原则声明
2. 在 CHANGELOG / 升级说明中明确标注此次行为变更
3. 评估 VAD 默认开启对短音频的潜在负面影响

### F-02 [P0] 基准测试缺少 WER/准确率指标

**发现位置**: DESIGN 第 4.4 节"`single_run` 返回指标"

**描述**:
基准测试收集的指标包括耗时、内存、RTF、segment 数量等**性能指标**，但没有任何衡量**转录质量**的指标。使用 edge-tts 合成音频的最大优势就是**天然拥有 ground truth 文本**（TTS 的输入文本），可以精确计算 WER（词错误率）。

没有 WER，基准测试无法回答最基本的三个问题：
1. `monologue` 的 `threshold=0.3` 有没有多捕获到本应被遗漏的语音？（以及有没有多引入幻听？）
2. `voicelines` 的 `threshold=0.6` 是否导致漏掉了台词？
3. 三个 profile 的转录质量是否有统计学差异？

设计文档说"数据驱动，所有参数默认值来自基准测试验证，而非直觉"（第 1 章原则），**但没有 WER 就无法"验证"——没有质量维度，只有性能维度的数据**。

**影响**:
- Sprint 1 的核心输出（三个 profile 是否有效）无法被量化评估
- Sprint 2 的模型大小 × Profile 矩阵对比失去质量基线
- 整个基准测试沦为"性能摸底"，而非"效果验证"

**建议修复方案**:
1. 在 `single_run` 指标中加入 `wer` 和 `cer`（字符错误率）
2. 存储 ground truth 文本（TTS 输入文本 + 拼接后自动生成 .txt 参考文本）
3. 使用 `jiwer`（Python 库，`uv add jiwer`）或 `evaluate` 库计算 WER
4. 验收标准中增加验收项：各 profile 的 WER 应在合理范围内（如 < 30%）

### F-03 [P1] M1 Air 被动散热在长测试中的降频问题未考虑

**发现位置**: DESIGN 第 2.2.3 节"M1 MacBook Air 约束检查"、第 4.2 节测试矩阵

**描述**:
设计文档详细计算了内存约束（9.5 GB < 16 GB ✅），但**完全忽略了 CPU 散热约束**。MacBook Air M1 是被动散热（无风扇），在持续高负载下必然降频。

关键数据点：
- 3 profiles × 4 durations × 3 repeats = 36 次运行
- 仅 30min 测试就有 3 × 3 = 9 次运行，每次 30min，合计 4.5 小时纯转录时间
- 加上 15min（9 次 × 15min ≈ 2.25h）和 5min（9 次 × 5min ≈ 45min）
- 如果按 30min → 15min → 5min → 1min 顺序执行，前两轮已经让 M1 升温到热平衡
- large-v3 int8 在 M1 CPU 上是几乎 100% 负载，持续 5-10 分钟后 SoC 温度突破 80°C 开始降频

**影响**:
- 30min 后几组的 15min/5min/1min 测试会受到**热累积效应**影响，数据不可比
- 同 profile/时长 的三次重复如果连续执行，第一次可能比后两次快（冷 vs 热）
- RTF 稳定性验收标准（标准差 < 15%）可能因为热效应而不通过，但不反映 profile 差异
- 线性增长假设（D-01）的验证会被降频混淆——30min 点的 RTF 可能因为降频而偏高

**建议修复方案**:
1. 在基准测试中**随机化测试顺序**（而非按 profile/时长分组），使热效应均匀分布
2. 每次运行间加入冷却间隔（如 60s，文档记录间隔时长）
3. 记录 CPU 温度（`pmset -g therm` 或 `osx-cpu-temp`）作为额外指标
4. 或：将 30min 测试单独安排在最后，并在结果中标注"可能受降频影响"
5. 验收标准补充：记录每次运行前的 SoC 温度

### F-04 [P1] `monologue` 的 `vad_threshold=0.3` 可能捕获非语音信号

**发现位置**: DESIGN 第 2.2.1 节"vad_threshold（语音检测灵敏度）"

**描述**:
设计文档为 `monologue` 选择 `threshold=0.3` 的理由是"捕获轻微说话声（如叹气、思考中的低声重复），避免漏字"。

但这个推理存在一个根本问题：**VAD 不区分"有意义的语音"和"口腔噪声"**。阈值越低，不仅捕获低声细语，也捕获：

- **呼吸声**（特别是靠近麦克风时）
- **咂嘴声**（lip smack）
- **牙齿摩擦声**
- **吞咽声**
- **喷麦声**（plosive burst）
- **衣物摩擦声**

在单人播客/演讲录音中，这些噪声非常普遍。0.3 的阈值可能把每个呼吸都标记为独立语音段，导致 segment 数量暴增但并不提高转录质量。

**影响**:
- segment_count 在 monologue 中可能异常高（远高于 voicelines），但这不代表"更多语音被正确识别"
- 可能增加幻听风险（Whisper 会尝试转译呼吸声）
- `vad_min_speech_duration_ms=500` 确实可以过滤掉 <500ms 的短噪声，但较长的呼吸（如深吸气后的停顿）仍可能被捕获
- 后续 Sprint 如果使用 segment_count 作为并行切分的分片依据，可能被此数据误导

**建议修复方案**:
1. **实验验证优先于直觉选择**：在基准测试中对比 `threshold=0.3`、`0.4`、`0.5` 三个候选值的 WER 差异
2. 如果数据不足以支持 0.3，考虑回退到 0.4 或 0.45（比默认略低但不极端）
3. 在测试语料中加入含呼吸声/口腔噪声的样本（可手动截取一段真实播客包含呼吸的部分）
4. 明确记录：该值是"待 Sprint 1 基准验证"状态，而非最终定值

### F-05 [P1] 边界条件缺失：<1s 音频 / 纯静音 / 采样率不匹配

**发现位置**: 全文未涉及

**描述**:
设计文档完整定义了正常路径，但对以下边界条件完全未定义：

**<1s 音频**:
- Whisper 本身可以处理短音频，但 VAD 的 `min_speech_duration_ms=250/500/100` 可能导致整段被过滤
- 结果是空 segments 列表，脚本打印空行，生成空 .txt 文件
- 用户无法区分"处理完成但无语音"和"处理失败"

**纯静音/无语音**:
- 同上，VAD 过滤掉所有内容 → 空输出
- 但用户可能以为工具坏了或出 bug

**采样率 ≠ 16kHz**:
- WhisperModel 内部使用 librosa 加载音频，支持重采样
- 但设计文档没有说明：如果输入的音频采样率极低（8kHz 电话录音），质量会显著下降
- 如果输入的音频采样率极高（96kHz 录音），重采样有额外计算开销
- Profile 系统是否需要加入采样率矫正？或者至少输出警告？

**多语言混合**:
- `language=None`（自动检测）可以处理混合语言，但 chunk_length=30 的 monologue 模式下，每个 chunk 都会重新检测语言，可能导致同一段音频的语言标签不断切换
- 明确指定 `--language` 时，混合语言片段会被强制用单语言模型处理，质量不可预测

**影响**:
- 这些边界在用户实际使用中一定遇到（有人会转录 0.5s 的录音片段，有人会转录纯背景噪音）
- 当前脚本遇到空 segments 会崩溃吗？回顾 Sprint 0 代码：`for segment in segments:` 如果 segments 为空，循环不执行，然后打印空行并输出空 .txt 文件。**不崩溃但无声失败。**
- 边界条件未记录，用户需要自己去翻代码才能理解行为

**建议修复方案**:
1. 在 CLI 层增加：音频时长检测，若 < 1s 则输出 warning
2. 在 CLI 层增加：VAD 过滤后若 segments 为空，输出 warning "未检测到语音内容"
3. 在文档中增加采样率说明章节
4. 增加 `--no-vad` 选项，允许用户在某些边界场景下绕过 VAD 过滤

### F-06 [P1] `chunk_length=30` 与 Sprint 2 外部切分的两层嵌套未讨论

**发现位置**: DESIGN 第 6.1 节"Sprint 2 预留接口" + 第 2.2.2 节

**描述**:
monologue profile 设置 `chunk_length=30`，即 **faster-whisper 内部** 30 秒切分处理。设计文档第 6.1 节预留了 Sprint 2 的外部切分接口：

```python
if profile.parallel:
    chunks = split_audio(audio_path, chunk_sec=300)  # 5min 外部切分
    results = parallel_map(transcribe_chunk, chunks)
    transcript = merge(results)
```

当两个切分层级并存时：

```
外部切分 (chunk_sec=300) ──┬── chunk 1 (0-300s) ──┬── internal chunk 1 (0-30s)
                           │                        ├── internal chunk 2 (30-60s)
                           │                        └── ...
                           ├── chunk 2 (300-600s) ──┬── internal chunk 1 (0-30s)
                           │                        └── ...
                           └── ...
```

**问题**:
1. 在外部 5min chunk 的边界处，是否会有 internal chunk 跨越边界的风险？实际上没有，因为外部 chunk 是物理切分后独立送给 WhisperModel，所以边界是干净的。但 internal chunk 在外部 chunk **内部** 的 30s 边界处可能截断句子
2. 如果 Sprint 2 的并行度较高（2-3 路），每个线程都在跑 internal chunk=30s 的 monologue，M1 的 CPU 和内存压力会倍增
3. 目前没有讨论这两个 chunk 层级的协调机制

**影响**:
- Sprint 2 设计可能因为 Sprint 1 的 chunk_length 选择而被迫调整
- 如果 monologue 的 chunk_length=30 是出于内存安全必须的，那 Sprint 2 做并行时每个线程的 monologue 仍然需要 30s chunking，但整体内存占用会按并行度放大

**建议修复方案**:
1. 在 Sprint 1 的文档中明确标注这个风险点
2. 考虑 monologue 在 Sprint 2 的并行版本中是否需要 `chunk_length=0`（Sprint 2 的外部切分已经控制了每个 worker 的音频长度）
3. 或在 Sprint 2 设计中对 monologue profile 做特殊处理

### F-07 [P2] `voicelines` 的 `threshold=0.6` 可能遗漏轻声台词

**发现位置**: DESIGN 第 2.2.1 节

**描述**:
`voicelines` 设定 `threshold=0.6`（高于默认 0.5），理由是有 BGM/音效时避免将音乐误判为语音。但在游戏场景中：

- 角色轻声台词（whispered lines）可能和背景音乐音量相当
- 角色在爆炸/战斗场景中说话时，语音的动态范围可能被压缩
- 有些角色刻意用气声说话（如潜行场景台词）

0.6 的阈值意味着语音信号的 VAD 信心得分必须 > 60% 才算语音。轻声台词可能只有 0.4-0.5 的 VAD 分数，会被过滤掉。

**影响**:
- 游戏场景中关键台词的转录缺失
- 用户（游戏开发者）可能因为台词漏转而对工具失去信任
- 与 monologue 的 0.3 形成鲜明对比——一个太激进，一个太保守

**建议修复方案**:
1. 基准测试中对比 `threshold=0.5`、`0.55`、`0.6` 三个值的 WER 差异
2. 可以使用更保守的 0.55 作为折衷
3. 或保持 0.6 但建议用户在重要场景辅助使用 `--language` 来改善检测

### F-08 [P2] VAD 参数差异缺乏数据支撑

**发现位置**: DESIGN 第 2.2 节

**描述**:
设计文档声称原则是"数据驱动"（第 1 章），但所有 VAD 参数的选择理由都是**逻辑推演而非实验数据**。例如：

- `vad_threshold`：0.3/0.5/0.6 来自推理，不是来自对真实音频的 VAD 曲线分析
- `vad_min_speech_ms`：500/250/100 也是基于场景直觉，不是基于语料库的语音时长统计
- `vad_min_silence_ms`：600/2000/300 同理

在没有任何数据的情况下说"数据驱动"是矛盾的。

**影响**:
- Sprint 1 的"基线摸底"本应提供数据来驱动参数选择，但现在基线数据要在 Sprint 1 基准测试后才产生
- 这是一种**先射箭再画靶子**的情况——先用直觉设值，再用基准测试"验证"（验证的基本是自己选的数，不太可能推翻自己）
- 如果没有数据，P0 的 F-02（无 WER）问题不修复，则永远无法验证参数选择

**建议修复方案**:
1. 明确标注所有 VAD 参数为"初始值（待基准验证）"
2. 在基准测试中至少对 `threshold` 做 A/B 对比（如 monologue 的 0.3 vs 0.4）
3. 将参数选择理由改为"假设"而非"结论"

### F-09 [P2] CLI 不支持 `--profile help` 列出可用 profile

**发现位置**: DESIGN 第 3 章

**描述**:
用户可能忘记有哪些 profile 可选。虽然有 `--help` 可以在参数描述中看到，但 `--profile help` 是一种更直观的探索方式。当前设计没有支持。

另外，`--profile` 的 help 文本虽然列出了三个值，但没有给用户足够的指引来判断"我该选哪个"。

**影响**:
- 用户体验不完整
- 用户可能在两个 profile 之间犹豫不定

**建议修复方案**:
1. 实现 `--profile help` 或 `--profile list` 参数
2. 在 help 文本中对每个 profile 给出简短用例

### F-10 [P2] `--model` 参数未做任何验证

**发现位置**: DESIGN 第 3 章

**描述**:
`--model` 参数接受任意字符串，直接传递给 `WhisperModel` 构造函数。如果用户输入不存在的模型名：

- `WhisperModel` 会尝试从 HuggingFace 下载，失败后抛出底层异常（如 `OSError`、`HTTPError`）
- 用户看到的错误信息不友好，没有提示可用模型列表
- 特别是如果网络不可用（如企业内网），错误信息可能指向网络连接问题而不是模型名问题

**影响**:
- 错误路径的用户体验差
- 新手用户难以诊断问题

**建议修复方案**:
1. 维护一个已知模型列表（`["large-v3", "large-v2", "medium", "small", "base", "tiny"]`）
2. 输入超出列表时，给出 warning + 提示列表
3. 或至少提供一个 `--list-models` 选项

### F-12 [P2] 缺少 CPU 温度/降频状态监测

**发现位置**: DESIGN 第 4.4 节

**描述**:
（此问题与 F-03 关联但不完全重叠。）F-03 说的是测试顺序，F-12 说的是运维数据采集。

即使解决了测试顺序问题，认知每次运行时的 CPU 热状态对数据解释至关重要。设计文档的 `single_run` 指标不包含任何与温度相关的字段。

**影响**:
- 如果某次运行的 RTF 异常高，无法判断是因为 profile 差异还是降频

**建议修复方案**:
1. 在基准测试脚本中采集 `pmset -g therm` 输出（显示 `CPU_Scheduler_Limit` 和 `CPUs_Available`）
2. 或使用 `osx-cpu-temp` 获取 CPU 温度近似值
3. 或至少记录运行时间戳以及测试序号，便于事后分析温升趋势

### F-13 [P2] 模型加载时间与转录时间未分离

**发现位置**: DESIGN 第 4.4 节

**描述**:
`single_run` 测量的是整个函数执行时间（从调用到返回），但其中包含模型加载时间。对于 1min 测试，模型加载时间可能是转录时间的数倍，这会：

- 使 1min 的 RTF 值看起来比实际高很多
- 使"线性增长"验证的数据点偏移（1min 的数据点会明显偏高）
- 4 个时长点的 RTF 可能看起来"不线性"，但只是加载成本摊薄效果

**影响**:
- D-01 线性假设验证的第一批数据可能有系统性偏差
- "RTF 稳定性"验收标准（标准差 < 15%）可能因为 1min 数据点而被破坏

**建议修复方案**:
1. 在基准测试中分离"模型加载"和"转录执行"两个阶段的计时
2. 或者：所有 profile/时长组合复用同一个已加载的模型实例（但这会影响峰值内存测量）
3. 合理方案：每轮 36 次运行只加载一次模型（测试前预热），记录整体加载时间一次

### F-14 [P2] Profile 语言字段声明与文档描述不一致

### F-15 [P2] `device="cpu"` 一刀切，缺少 mps 对比数据

**发现位置**: DESIGN 第 5 章 ADR 隐含 & 第 6.2 节

**描述**:
设计文档采用 `device="cpu"` 的理由是"mps 有兼容性问题"。但：

1. 当前 Sprint 0 代码的**注释**（第 21-23 行）明确说：
   > 4. device 用 mps（macOS Apple Silicon GPU 加速），遇到兼容问题回退到 device="cpu"。

   说明原设计意图是 mps 优先，cpu 作为回退。设计文档反其道而行之——cpu 作为唯一选择。

2. 没有提供任何 benchmark 数据证明 mps 在当前 faster-whisper + torch 版本下"不能用"。

3. 如果 mps 可用，推理速度可能提升 2-3 倍，这对 30min 测试的可行性有巨大影响。

**影响**:
- 可能浪费了 Apple Silicon 的 GPU 加速能力
- 16GB M1 在 CPU-only 模式下做 30min 转录效率低下
- Sprint 2 的并行设计如果基于 CPU-only 的 RTF 数据做决策，可能过度悲观

**建议修复方案**:
1. 在基准测试中增加一列：使用 `device="mps"` + `compute_type="float16"` 或 `int8` 的对比数据
2. 至少做 1min 和 5min 对比测试，验证 mps 的兼容性和加速比
3. 如果 mps 在 80% 场景下可用，可以设为自动检测：mps可用则 mps，否则 fallback cpu

### F-11 [P2] `-stream_loop` 重复同一段 1min 音频过于人工化

**发现位置**: DESIGN 第 4.3 节

**描述**:
基准测试通过将同一段 1min TTS 音频用 `-stream_loop` 拼接出 5min/15min/30min。这意味着：

- 5min = 同一段话重复 5 遍
- 15min = 同一段话重复 15 遍
- 30min = 同一段话重复 30 遍

这种测试音频的特点：
- 没有语音自然变化（同一人声、同一语速、同一语调、同一内容）
- 没有停顿变化（TTS 的停顿模式完全一致，每次循环完全对齐）
- 没有录音环境变化（同一段音频循环，噪声特征一致）
- VAD 模式对相同内容逐字重复，可能导致 Whisper 的语言模型产生过拟合（在后几遍循环中更容易预测）

**问题**:
- segment_count 数据完全失真——EOS（句尾）在每个循环边界都会被 VAD 检测到，segment 数量成倍增长
- 但真实长音频不会这样整齐地分段
- RTF 可能偏优（模型在重复输入中可能利用缓存）

**影响**:
- segment_count 不能反映真实场景的分段模式
- 线性假设验证虽然可用，但结论的泛化性有限

**建议修复方案**:
1. 用多段不同的 TTS 文本拼接（而不是同一段重复），模拟真实音频的内容变化
2. 在拼接处插入不同长度的静音段（模拟真实停顿变化）
3. 或使用真实音频数据集（LJSpeech、Common Voice 等）拼接，不受限于 TTS 合成

### F-16 [P3] `temperature=0.0` 全 greedy 解码，无 fallback 策略

**发现位置**: DESIGN 附录 A

**描述**:
三个 profile 的 `temperature` 均为 `0.0`（fully greedy decoding）。这表示：

- 每次解码选择最高概率的 token
- 没有探索性，不会产生多样的转录候选
- 某些低置信度片段可能因为缺乏 fallback 而错误

faster-whisper 支持 `temperature` 参数，当传递一个列表时（如 `[0.0, 0.2, 0.4, 0.6]`），如果 `temperature=0.0` 的结果在某些段落的置信度低于阈值，会自动 fallback 到更高的温度。

**影响**:
- 边缘场景（噪声环境、口音、生僻词）的转录质量可能不如有 fallback 的方案
- 但 impact 有限，因为 Sprint 1 不强调极端场景

**建议修复方案**:
1. 明确记录这是 Sprint 1 的简化选择
2. Sprint 2 可以考虑引入温度 fallback 策略
